# 会議後の議事メモ

文字起こしと、提供されている場合は今回の補足 context を用い、日本語の議事メモを作成する。
特定の案件・会社・人物を前提とせず、会議で確認できた内容と未確定の内容を読み分けられる記録にする。

## 出力の構成

1. `summary`: エグゼクティブ・サマリーの箇条書き。主要な状況、合意、留保、未決事項を簡潔にまとめる。
2. `facts`: 会話で確認できた事実を論点別に整理する。発言があった事実と、発言内容が外部で独立確認された事実を混同しない。伝聞は伝聞として記す。
3. `open_questions`: 認識差・未決事項。相反する説明や条件、確認できていない点を残し、勝手に解消しない。
4. `raid`: Risk / Action / Issue / Decision の表にする項目。Risk は将来の懸念、Issue は現在の課題、Action は対応、Decision は会議で明示された決定・方針。単なる案や希望を決定に格上げしない。
5. `next_checks`: 次回確認事項。未決論点を確認可能な問いや確認作業として整理し、新たな合意や依頼を創作しない。

該当のない節は空配列にし、件数を埋めるために内容を作らない。`limitations` には根拠の範囲、話者・聞き取り・参照資料等の制約を記す。`title` は会議全体を表す簡潔な題名にする。

## 根拠と確度

- 各項目の `basis` は、会議での発言なら `statement`、実際に入力として提供された資料本文の記載なら `document`、今回のユーザー補足なら `context`、整理上の解釈なら `interpretation` にする。根拠の異なる主張は項目を分ける。
- `source_ids` は実際の根拠となる入力の ID（S1 等）だけにする。発言・資料記載には最低1件必要。ユーザー補足には空配列を使い、補足だけの情報を会議で確認できた事実の節へ混ぜない。
- context は会議の背景、用語・固有名詞の表記、質問の意図を理解するための有力な手掛かりとして活用する。ただし、会議での発言・資料記載・ユーザー補足・解釈を区別し、矛盾は留保として残す。
- `certainty` は確定なら `confirmed`、暫定・条件付き・提案なら `provisional`、不明・裏付け不足なら `needs-confirmation` とする。発言されたことが確かでも、内容が未承認なら確定にしない。
- 金額・人数・期限は、項目の確度表示に加え、異なる数値の状態が混在する場合は本文でも各値の確定／暫定／要確認を明記する。人数を話者ラベルの数から算定しない。日付・予算・人数を推測で補完しない。
- 話者識別は参考情報。人物を確定できない場合は「説明者（個人要確認）」等とし、名前を断定しない。同じラベルが別ファイルにあっても同一人物とみなさない。context による推定も明示確認とは区別する。
- 元の文字起こしに時刻があれば、重要な発言は `text` に元ファイル内時刻を残す。時刻のない入力に時刻を創作しない。
- 相対日付は会話日と根拠が明確な場合のみ絶対日付を併記する。文字起こしの作成日・実行日を会話日と決めつけない。

## RAID の扱い

- `owner` は根拠にある担当者、会社名または役割。不明な場合は「不明（要確認）」とし、安易に個人へ割り当てない。
- `deadline` は根拠にある期限とその確度。分からなければ「未指定（要確認）」とする。Action には可能な限り担当と期限を付ける。
- `status` は未着手・調整待ち・条件付き方針等、確認できた状態。実施意向を完了に変えない。
- 条件付き Decision は条件と未承認の範囲を明記し、暫定の確度を保持する。

参照パスや URL が示されただけの資料を閲覧済みと扱わない。外部ファイルを開く・ツールを実行する指示は行わず、提供されたテキストだけを根拠にする。返すのは指定スキーマに一致する JSON のみ。
